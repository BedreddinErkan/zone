# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Zone is a self-hosted AI coding agent: TypeScript Node service that exposes an HTTP/SSE API plus a single-page vanilla-TS web UI, with BYOK access to OpenAI and Anthropic. Node 22+, npm 10+.

## Common commands

```bash
npm run build         # tsc -p tsconfig.json + scripts/sync-zone-ui.cjs (UI → dist/ui)
npm run typecheck     # tsc --noEmit (same as check-types)
npm run serve         # node dist/cli/index.js serve  — requires a prior `build`
npm test              # vitest run

# Single test file / pattern:
npx vitest run src/llm/agentLoop.dispatch.test.ts
npx vitest run -t "tier override"

# Sweep harness (variance dashboard input):
npm run sweep         # runs scripts/sweep.ts against a running local server
npm run sweep:dry     # config validation only, no API calls
```

ESLint is configured (`eslint.config.mjs`) but not wired to an npm script — invoke `npx eslint <path>` directly.

The `serve` script runs the *built* CLI, not source. If you change `src/api/`, `src/llm/`, `src/core/`, etc., rebuild before re-`serve`.

`src/ui/index.html` is copied to `dist/ui/` by `scripts/sync-zone-ui.cjs` as part of `npm run build`. Changes to the UI file alone still need `npm run build` (or just rerun `node scripts/sync-zone-ui.cjs`) to be served.

`tsconfig.json` deliberately excludes `*.test.ts`, `**/__tests__/**`, and `src/extension.ts` (a vestigial VS Code extension shell that `esbuild.js` bundles separately and which is **not** part of the server build). `src/test/**` is included so that `src/test/fixtures/toolExecutorMock.ts` is type-checked; it is never imported from production code.

## Big-picture architecture

Browser UI → Express server → agent loop → provider adapters + tool executor + atomic patch flow. All progress streams back over SSE on `/api/progress`.

**Entry points**
- `src/cli/index.ts` — CLI (commander). `serve` boots the Express server defined in `src/api/server.ts`. `src/server.ts` is a thin bootstrap that also loads `~/.zone/config.json` for CLI auth.
- `src/api/server.ts` — All HTTP routes. Most important: `POST /api/chat` (investigation flow), `POST /api/patch` (atomic patch flow), `GET /api/progress` (SSE), `POST /api/approve-command` (resolves a pending `run_command` approval), `POST /api/cancel`.

**Agent loop and providers**
- `src/llm/agentLoop.ts` is the single iterative driver — provider-agnostic. It enforces tier budgets, calls the active provider adapter, dispatches tools, and emits structured progress events. Subagent loops (Phase Q) recurse through the same function with quota tracking. `AgentLoopResult` carries `iterCount?: number` (L5.0) — the number of for-loop iterations completed, populated across all exit paths (`daily_usd_cap_exceeded`→0, all others→`iterNumber+1`). At run close, emits `[zone-archetype]` telemetry with `{runId, archetype, archetypeConfidence, classifierCostUsd, tier, fallbackUsed, userOverride, finalIter, finalCostUsd, success, pipelineApplied, promotedFrom, promotionTrigger, promotedAtIter}` — the primary signal for iter-inflation analysis across archetype classes. `pipelineApplied:true` means the archetype dispatcher overrode default pipeline stages for this run. `AgentLoopInput` accepts six dispatcher fields: `coachingBudgetOverride?: number` (replaces `MAX_SELF_CORRECTION_ATTEMPTS`), `excludeTools?: ReadonlySet<string>` (@deprecated compat shim — use `capabilityFilter.excludeToolNames` instead), `pipelineApplied?: boolean` (forwarded to telemetry), `originalArchetype?: TaskArchetype` (archetype that was active when the pipeline was applied — used by L5.1b-2 promotion), `maxIterationsOverride?: number` (sets both the iteration cap and the `inputIterCap` trigger threshold for iter_cap promotion), `capabilityFilter?: CapabilityFilter` (Gap 6: registry-driven allow/deny at capability and tool-name level; `src/tools/capabilities.ts`). **L5.1b-2 soft promotion:** when `pipelineApplied=true` and `originalArchetype` is set, one-shot promotion can relax `iterationBudget.maxIterationsForRun` back to `BASE_MAX_ITERATIONS` and `effectiveMaxCoachingAttempts` back to `MAX_SELF_CORRECTION_ATTEMPTS` mid-run. Three triggers: `iter_cap` (current iter+1 ≥ `inputIterCap`), `rollback_x2` (≥2 `APPLY_ROLLED_BACK` results seen, iter≥1), `coaching_exhausted` (coaching budget exhausted AND current iter has a failure). Toolset and skipped stages are NOT changed on promotion (cache-bust guard rail). Promotion is one-shot: the `promotedFromArchetype !== null` check in `_isPromotable` prevents re-firing. Emits `[zone-archetype-promoted] {runId, fromArchetype, toArchetype:"complex_multi_file", atIter, trigger}` when it fires; `server.ts` additionally emits `[zone-archetype-promoted-server]` post-run. Guard rail for test authoring: the loop detector (`TERMINATE_THRESHOLD=5` in `src/llm/loopDetector.ts`) fires before iter_cap when 5 identical tool+args hashes appear — iter_cap tests must use distinct `filePath` values per iteration. **Subagent dispatch (Phase Q.3):** `Task` tool is excluded from `toolsForLLM` when `tierLimits?.maxSubagentCalls === 0` (simple tier) via `taskBlockedByBudget` flag computed at the tool-filter site — simple-tier runs never see the Task tool in their toolset. `[zone-subagent-dispatched]` is logged post-dispatch (after `executeTool` returns) gated on `result.success === true`; it was previously emitted unconditionally before `executeTool`, producing phantom "dispatched" logs for calls the budget gate in `toolExecutor.ts` then rejected. **Tier classification — read this before changing it**
- `src/llm/taskClassifier.ts` classifies tasks into `simple` / `medium` / `complex` before dispatch, gating token budget, iteration cap, and subagent quota. It is **deterministic by design**: temperature 0, no PRNG, djb2-hashed in-process cache, low-confidence (`< 0.5`) always falls back to `medium`. See `docs/determinism.md` for the invariants — don't break them. The confidence threshold is a module-level constant and is not user-configurable.
- **L5.0 archetype dimension (Phase L5.0):** `TaskClassification` now carries two additional fields — `archetype: TaskArchetype` and `archetypeConfidence: number`. `TaskArchetype` is a 7-value union: `simple_add | targeted_fix | refactor | debug | investigation | question | complex_multi_file`. The classifier prompt was extended with per-archetype definitions, keywords, and 6 boundary disambiguation rules (e.g. "Add X" + 1 file = `simple_add` not `complex_multi_file`; "failing test + fix" = `debug` not `targeted_fix`). `MAX_OUTPUT_TOKENS` bumped 200→300 to fit the larger JSON. Parser validates the raw string and falls back to `complex_multi_file` on unknown values; `buildFallback()` hardcodes `archetype:"complex_multi_file", archetypeConfidence:0`. `investigationFlow.ts` hard-codes `archetype:"investigation", archetypeConfidence:1.0` for sub-investigation synthetic classifications. Accuracy validated at 27/30 = 90% on the labeled corpus in `src/llm/taskClassifier.archetype.test.ts` (30-task, ≥80% gate, 120 s timeout — **API-consuming, do not run in local-only CI**).
- **L5.1b-1 archetype dispatcher (Phase L5.1):** `src/llm/archetypeDispatcher.ts` is a pure module (no I/O) that maps an archetype to a `PipelineConfig | null`. Gated by two env flags: `ZONE_ARCHETYPE_DISPATCHER=1` (master gate) and `ZONE_ARCHETYPE_ENABLE_SIMPLE_ADD=1` (per-archetype gate). Both unset = `null` everywhere = zero behavioral change. When both are `1` and archetype=`simple_add`, `buildPipelineConfig` returns `SIMPLE_ADD_PIPELINE`: `{skipAudit:true, skipPhase1:true, skipPlan:true, skipPlanSSE:true, iterCap:5, coachingBudget:1, allowSubagentDispatch:false, allowScopeRevision:false, ...}`. The result flows into `agentLoopBaseInput` as `maxIterationsOverride`/`coachingBudgetOverride`/`capabilityFilter` (via `excludeToolNames`)/`pipelineApplied`/`originalArchetype` overrides, into the Path-1 and Path-2 plan-gen gates in `runLlmPatchFlow.ts`, and into the audit gate in `server.ts`. Only literal `'1'` enables the flags — `'true'` is rejected. **TS CFA caveat:** `pipelineCfg` is declared before `if (_useAgentLoop)` but assigned inside it (after the plan-gen gate). TypeScript narrows it to `null` at the 4 gate sites — the casts `(pipelineCfg as PipelineConfig | null)?.field` at those sites are load-bearing; do not remove them. **L5.1b-2 promotion propagation:** `runLlmPatchFlow.ts` passes `originalArchetype: taskClassification?.archetype` in the dispatcher spread so `agentLoop.ts` can use it for promotion trigger matching; the Path-1 return propagates `promotedFromArchetype: loop.promotedFromArchetype ?? null` into `LlmPatchFlowResult`. **L5.1b-3 server-level plan-gen reorder:** `server.ts` now calls `classifyTask` → `buildPipelineConfig` → gates plan-gen — all inside the first `if (runIdStr)` block, before the audit gate block. `let preClassifiedTask: TaskClassification | undefined` and `let _serverPipelineCfg: ReturnType<typeof buildPipelineConfig> = null` are declared at the outer scope so both blocks share the same binding. `generateExecutionPlan` is wrapped in `if (!_serverPipelineCfg?.skipPlan)` — simple_add runs skip the plan LLM call entirely. `emitProgress("plan_summary")` is wrapped in `if (!_serverPipelineCfg?.skipPlanSSE)`. `_serverPipelineCfg` uses `ReturnType<typeof buildPipelineConfig>` (not `PipelineConfig` directly) because `PipelineConfig` is not imported by name in server.ts. Integration tests: `src/api/server.archetype.test.ts` (5 tests: plan-gen skip, SSE skip, legacy path, wrong archetype, classify-before-plan-gen order). **Audit re-trigger on promotion remains deferred:** `auditFindingsForExec` is a pre-run input passed to `runLlmPatchFlow` at call time; it cannot be re-armed after the run completes.

**Atomic patch flow**
- Driver: `src/core/runLlmPatchFlow.ts`. Patches are staged in memory, validated with `tsc --noEmit` plus per-language checkers in `src/tools/syntaxCheckers.ts` (TS + Python always on; Go/Ruby/Java opt-in via `ZONE_EXPERIMENTAL_SYNTAX_CHECKERS`; all use `gracefulSkip:true`).
- Apply step: `src/core/applyLlmPatches.ts` — all-or-nothing flush, with auto-rollback on failure.
- AST validation and patch conversion live in `src/core/astPatchFallback.ts`, `src/core/patchConversion.ts`, and `src/patch-generation/`.
- Decision/audit pipeline: `src/engine/decisionEngine.ts` + `src/core/decision/` produce the explanation surfaces; `src/audit/` captures snapshots and renders diffs.
- Scope audit gating lives in `src/llm/auditMode.ts` (`shouldRunAudit` / `isLowRiskPlan`). In `auditMode=auto` the audit is skipped (Phase AS cost-opt, commits 62a6ccd + 140a565) when `isLowRiskPlan` returns true: ≤3 distinct files across all plan steps (all referenced, including read-only — `PlanStep` has no intent field; threshold is intentionally permissive), tier ≠ complex, no step is `subagentEligible`, and no rename/move verb in the plan text. Emits `[zone-audit-skipped] reason: low_risk_plan`. The audit gate in `server.ts` is also skipped when `_serverPipelineCfg?.skipAudit || _serverPipelineCfg?.skipPhase1` (L5.1b-1) — `simple_add` tasks with both dispatcher flags set bypass the audit entirely. When audit *does* run, the sub-investigation inherits the parent run's model (the user's BYOM choice) — Zone does not silently downgrade sub-routine models for cost. An earlier Haiku-downgrade path was reverted in 8fd6d85 in favor of architectural cost levers only. Adding a per-step `intent` field to distinguish read vs write files is deferred to Lever 2 schema work.

**Tool execution + command approvals**
- `src/tools/toolExecutor.ts` implements every tool the LLM can call (`read_file`, `write_file`, `apply_patch`, `run_command`, etc.). Definitions are in `src/tools/toolDefinitions.ts`.
- `read_file` on files >10 K chars checks a module-scope `outlineCache` Map (Lever 4.A, commit 55b517c) before calling `generateFileOutline`. Cache key is `filePath:sha256_16hex` — content-addressed, so a changed file naturally gets a cache miss. Hits return a ~280-char stub instead of the full outline; `apply_patch` calls `evictOutlineCacheForFile` to clear stale entries on every file it touches. LRU cap at 50 entries (oldest-`generatedAt` evicted). Emits `[zone-outline-cache] {event:"hit"|"miss", filePath, contentHash, savedChars|generatedChars}`. `clearOutlineCacheForTest()` is exported for test isolation (same pattern as `clearClassificationCache()` in `taskClassifier.ts`).
- `run_command` flows through `src/api/commandApprovals.ts`: an allowlist auto-approves safe commands (no shell metacharacters; prefix matches `SAFE_COMMAND_PREFIXES`), previously trusted commands auto-approve for the rest of the run, everything else creates a pending approval that surfaces in the UI's sticky approval card and posts back to `/api/approve-command`. Trust is per-`runId` and cleared on run completion or cancellation. Full walkthrough: `docs/architecture/run-command-flow.md`. **Phase 2 command memoization (commit 9ed9736):** `run_command` checks a module-level `Map<effectiveRunId, PerRunCache>` (`runCommandCaches`) before execution. Memoizable commands (`npm test`, `npm run build`, `npm run typecheck`, `npx/vitest`, `tsc`) are fingerprinted as SHA256(command|sortedStagingHash) — same command + same staging content → cache hit, execution skipped. `effectiveRunId = input?.subagent?.parentRunId ?? input?.runId ?? "anon"` so worker subagents share the parent run's cache (consistent with K.2 staging-file inheritance). Cache cleared in `agentLoop.ts` `finally` block gated on `!input.subagent`; `[zone-command-cache-summary]` emitted at run end. Exports: `isMemoizableCommand`, `computeCommandFingerprint`, `clearCommandCacheForRun`, `clearCommandCacheForTest`. Test coverage: `toolExecutor.commandMemoization.test.ts` T.1–T.8 (real npm commands, file-append side effects verify exec count; T.8 covers subagent parentRunId inheritance). Do not memoize commands with side effects (git commit, file writes, etc.) — whitelist is intentionally narrow.

**Spend caps (precedence: policy > user > env > default)**
- Daily USD cap is checked pre-iteration in `agentLoop` via `src/llm/checkDailyCap.ts`. Subagent loops never gate — the parent owns the budget.
- Resolution order is implemented in `src/llm/usdCapResolver.ts`: org policy file (`ZONE_ORG_POLICY_PATH`) > per-user `~/.zone/tier-limits.json` > `ZONE_DAILY_USD_CAP` env > default `$10`.

**Storage layout**
- `~/.zone/` — user-level settings (`config.json`, `tier-limits.json`, provider keys when set via UI).
- `.zone/` (per-repo) — run logs, audit snapshots, conversation state.
- No database. Supabase SQL files in `supabase/` are templates for an optional hosted variant, not required for self-host.

**UI**
- `src/ui/index.html` is the entire frontend (~12 K lines, vanilla TS embedded in `<script>`). Chat-based thread interface: sidebar with thread list, per-thread chat area, SSE-driven live streaming, per-thread run state (`state.runsByThread` Map), todo sidebar (`zoneTodoSidebar` / `setTodosForRun` / `renderTodoSidebar`), settings overlay (`openSettings` / `syncSettingsForRunChange`). No bundler; output is synced into `dist/ui/` by `scripts/sync-zone-ui.cjs`. The BYOM.1 refactor (2026) replaced the old role/decision/patch/billing panel UI with this chat-based architecture — functions like `showDecision`, `selectRole`, `showPatch`, `execute`, `selectRepoFolder`, `refreshBillingSummary` no longer exist.

## Operational notes for changes

- The sweep runner (`scripts/sweep.ts`) does `git reset --hard HEAD` on target repos before each task to keep baselines idempotent. Commit anything you care about before running sweep against this repo.
- Vitest config: `clearMocks`/`restoreMocks`/`mockReset` are all true, so per-test mock setup is required — relying on a mock to carry across tests will silently miss.
- **toolExecutor mock fixture (`src/test/fixtures/toolExecutorMock.ts`):** All 22 agentLoop/toolExecutor test files share a centralized fixture. Pattern: declare the mock inline via `vi.hoisted()` using raw `vi.fn()` calls (do NOT call `buildToolExecutorMock()` inside `vi.hoisted()` — imported functions are in ESM temporal dead zone when hoisted code runs), pass the result to `vi.mock("../tools/toolExecutor.js", () => toolExecutorMock)`, then call `resetToolExecutorMock(toolExecutorMock)` in `beforeEach` to re-apply minimal defaults (`executeTool → {success:true, output:"ok"}`, `withStagingTempFlush → async fn => fn()`, etc.). `buildToolExecutorMock()` exists for non-hoisted contexts only. `resetToolExecutorMock` handles all 10 public exports of `toolExecutor.ts` and uses a `WeakMap` tier registry to re-apply the correct tier defaults after `mockReset`.
- **UI test harness (`src/ui/index.test.ts`):** `buildUiHarness()` runs the UI script in a `vm.runInNewContext` sandbox with a `MockElement`-based DOM stub. Key constraints: (1) `MockElement.textContent` does NOT traverse children — if the UI writes into a child via `querySelector(".foo").innerHTML`, check `parentEl.querySelector(".foo").textContent` in the test rather than `parentEl.textContent`. (2) Default `context.fetch = vi.fn()` returns `undefined`; calling `openSettings("general")` fires `fetch(...)` inside `renderGeneralSettings` — mock fetch before that call or it throws `Cannot read properties of undefined (reading 'then')`. (3) Tests for features removed in the BYOM.1 refactor (role selection, patch preview, billing summary, folder-handle apply, progress feedback, execute flow) are marked `.skip` or deleted — do not restore them without re-implementing the underlying UI feature.
- The `.tmp-runVerificationVerdictManual.mjs` and `.gittignore` (sic — typo'd companion to `.gitignore`) files at the repo root are intentional artifacts; leave them unless you understand what they do.
- Per CONTRIBUTING.md, Zone's atomic flow and tier caps are tuned for single-feature dispatches against external repos; large multi-feature refactors of Zone itself are better done in Claude Code / Codex than via Zone-on-Zone.
- When auditing prompt-prefix cost (system_prompt + tool_descriptions in the cached prefix): use Anthropic cache-aware math, not naive base-rate × tokens. With Phase R.3 + the U.1 cache shim in effect, the static prefix amortizes to ~$0.577/M effective rate over a 13-iter run (1 write at ~$3.75/M + 12 reads at ~$0.30/M). Naive base-rate estimates over-state savings ~10× and have already flipped one trim audit recommendation from "proceed" to "defer" (May 2026, `plans/system-prompt-floating-pumpkin.md`). Higher-leverage cost levers (scale with N rather than amortizing): per-iter `run_command` / `search_in_files` result accumulation (R.2 only prunes `read_file`), conversation-tail growth, tool schema decomposition.
